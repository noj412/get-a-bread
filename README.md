# 搜岗助手

将搜索计划、搜岗批次、命中岗位、个人证据和筛选依据放在同一个本机工作台。这个版本是可运行的流程原型，GitHub 仓库可用于管理代码与公开演示结构。

## 启动

需要 Python 3.9 或更高版本，使用 Python 标准库。

```sh
python3 server.py
```

浏览器打开 http://127.0.0.1:8876 。端口可通过 `--port` 修改，本机数据默认保存在 `data/workbench.sqlite3`，可通过 `--data-dir` 指定目录。

在“搜岗批次”点击“载入虚构示例”体验流程。示例公司、JD、能力证据均为虚构，不属于真实推荐。

## 六个页面

|页面|解决的问题|
|---|---|
|搜岗总览|查看本轮批次、去重结果和待跟进记录|
|搜索计划|保存搜索词、城市、来源及个人经历依据|
|搜岗批次|查看每个搜索词执行结果、读取量、登录或连接阻塞|
|岗位结果|查看原JD、链接、命中词、匹配证据和跟进状态|
|素材与能力|保存本人行动、来源及职责边界，按六个维度组织|
|筛选逻辑|解释发现、核验、去重、硬筛、证据匹配和回读过程|

## 自动化接入

当前已实现的数据链路如下。

```mermaid
flowchart LR
    A[浏览器或其他采集器] --> B[批次JSON]
    B --> C[导入校验与SQLite事务]
    C --> D[规范化链接去重]
    D --> E[搜索词与批次追踪]
    E --> F[岗位与逐项评估展示]
    F --> G[跟进记录与投递日期]
    H[个人证据库] --> F
```

浏览器或聊天代理读取真实岗位详情后，将 `example.json` 的 `run` 和 `jobs` 结构交给 `/api/import`。同一规范化URL合并为一条岗位，多次命中的批次继续保留。导入不会覆盖已有跟进状态、投递时间和不匹配原因，JD改变时旧评估失效。

自动化执行记录由采集器提供。每个来源、关键词、城市对应一个批次，失败时也提交空 jobs 数组与具体阻塞信息。

```sh
curl http://127.0.0.1:8876/api/import \
  -H 'Content-Type: application/json' \
  --data-binary @example.json
```

|接口|用途|
|---|---|
|GET /api/state|读取完整本机状态|
|POST /api/import|原子导入搜岗批次及JD，返回新增和更新回执|
|POST /api/decision|记录岗位状态、原因及历史；首次标已投递时记投递日期|
|POST /api/material|保存搜索计划或个人证据|

每个岗位可附 `review`，包含 `verdict`、`strength`、`gaps`、`mapping`。mapping 每行是“JD要求、证据来源及本人行动、证据判断”。生成评估的代理应先核对原始材料。当前服务展示导入评估，未自动生成匹配分数。

## 证据与筛选规则

六个维度是人群与需求判断、渠道获客、触达与资源分配、转化与销售承接、数据与商业回收、项目协作与交付。维度用于组织证据，不代表每个岗位都必须具备全部维度。

先按用户明确的地点、薪资、行业、公司规模和外包条件核验，再逐项拆解核心职责、必备要求与加分项。正文与标题信息冲突时保留冲突，未知项保持未知。刷新时间、HR活跃时间和首次发布日期分别记录。关键词与正则负责发现候选，核心职责判断由原JD和真实经历支持。

用户将岗位标为不匹配时保存原因。缺少原因时留待对话确认。相似岗位排除需要已确认的原因支持，不把一条标记自动扩大为整个行业或职类禁区。

今日投递数按 Asia/Shanghai 统计已标记已投递且投递日期为当天的岗位。该数来自本机记录，平台实际申请结果需采集器或本人同步。撤回已投递状态后历史记录仍保留，重新标记沿用首次投递日期。

## GitHub 与个人数据

仓库文件包含代码、流程说明和虚构样例。运行数据库、简历、证书、Excel、浏览器登录态和环境变量已加入 `.gitignore`。新增数据文件仍需在发布前检查。真实素材可保存在本机数据库，在界面添加；导出的备份含个人数据，应按个人数据处理。

当前服务只绑定本机127.0.0.1，不含远程登录和用户认证。GitHub保存代码后仍需在本机运行 Python 服务；GitHub Pages 无法运行这个 SQLite 后端。
